# 使用场景与验收设计

以下六个场景是本项目提出的落地方案，尚未执行。它们将[能力矩阵](CAPABILITIES.md)中的候选技能映射到业务任务，不代表上游已提供完整端到端系统。

## 场景 1：网站发布前回归

- **触发**：开发者修改表单、登录或导航后，检查核心路径。
- **输入**：本地应用、3—5 条关键路径、测试账号与预期状态。
- **技能候选**：网页测试；界面质量检查作为补充。
- **流程**：准备隔离数据 → 执行成功和失败路径 → 保留断言与截图 → 修复后复测。
- **交付**：通过／失败清单、复现步骤、必要截图与测试脚本。
- **验收**：每条路径有可观察断言；错误输入不被误判成功；结果可重复。
- **边界**：截图正常不代表交互正确，本地通过不能覆盖真实部署全部条件。

## 场景 2：固定格式经营报表

- **触发**：运营每周汇总订单、渠道或库存明细。
- **输入**：脱敏数据、字段说明、指标口径和现有模板。
- **技能候选**：XLSX；若需汇报材料，再评估文档或演示文稿技能。
- **流程**：核查数据 → 统一字段 → 按口径计算 → 写入表格 → 重算并对账。
- **交付**：可编辑报表、异常行列表、来源与假设说明。
- **验收**：总额和行数对应源数据；退款、空值与重复行有处理规则；公式抽样复算正确。
- **边界**：口径不清时应标注或澄清，不能将模型猜测当成业务事实。

## 场景 3：数据库慢查询排查

- **触发**：开发者发现列表接口变慢或连接拥塞。
- **输入**：SQL、表结构、索引、执行计划、数据规模和基准负载。
- **技能候选**：Supabase Postgres best practices。
- **流程**：理解语义 → 建立基线 → 提出最小修改 → 隔离环境比较 → 检查其他查询影响。
- **交付**：原因分析、候选变更、前后指标与回退方案。
- **验收**：结果集合一致；同一数据和负载下多次比较；兼顾写入代价。
- **边界**：新增索引不是无成本动作，规则指导不能替代负载测试。

## 场景 4：竞品资料整理

- **触发**：产品人员需要比较公开功能或定价说明。
- **输入**：竞品列表、资料范围、比较字段与截止日期。
- **技能候选**：网页数据获取＋表格／文档输出，具体包需要进一步核验。
- **流程**：获取页面 → 记录时间和来源 → 对齐口径 → 标注缺失 → 制作对照表。
- **交付**：带来源的比较表、信息缺口与分析建议。
- **验收**：关键结论可追溯；未知值不编造；价格注明日期和条件。
- **边界**：登录或渲染条件可能导致提取不完整；抓取成功不等于事实完整。

## 场景 5：跨系统线索分发

- **触发**：表单提交后，校验、去重、写入客户系统并生成通知。
- **输入**：事件样例、字段映射、去重规则和测试连接。
- **技能候选**：n8n workflow patterns＋目标系统工具。
- **流程**：验证输入 → 标准化 → 按唯一键去重 → 写入测试系统 → 记录结果。
- **交付**：可审查的工作流和测试记录。
- **验收**：重放不会重复建档；缺字段进入错误分支；服务失败可恢复。
- **边界**：凭据、访问权限和外部发送授权须由运行环境解决，技能不自动提供。

## 场景 6：团队知识标准化

- **触发**：希望减少重复解释审查规范、模板和交付要求。
- **输入**：已验证流程、正反例、模板与维护负责人。
- **实现方向**：借鉴现有技能结构，编写团队专用技能；属于定制建设。
- **交付**：小范围技能包、版本记录、适用及不适用测试案例。
- **验收**：目标任务正确触发；无关任务不受干扰；符合团队要求；升级可回退。
- **边界**：过长或矛盾的说明可能造成干扰，应先验证一个窄任务。

## 建议试点顺序

业务背景尚未明确时，先从场景 1 或 2 选一个，两者通常较容易准备样例和检查结果。已有数据库基准环境时可优先场景 3。场景 5 涉及多系统状态，宜在单系统流程稳定后考虑。

顺序来自输入准备、验证难度和外部依赖的初步分析，不是实测排名。
