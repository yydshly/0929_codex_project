# 对你的意义与采用建议

## 1. 判断依据

已知事实：你正在建立开源项目研究集，希望每个项目有独立编号、能力分析、场景判断和可持续保存的资料；本仓库也预留了可选 Web 演示。尚不知道你的职业、开发经验、团队规模和生产系统情况。因此下面按当前研究工作与未来可能的开发工作分别建议，不假设你已经有上线需求。

## 2. 当前能得到什么

### 把一次聊天变成可持续的研究

`context-engineering` 的方法适合把项目来源、研究目标、已知事实和未决问题放到合适的位置。结合 `documentation-and-adrs` 对决策理由的记录方式，可以让下次继续研究时知道“为什么这样判断”，减少重复解释。

这里是方法迁移：上述技能原本服务于代码项目。针对开源库研究，应明确产出是事实清单、证据与适用性结论，不能假设原文已经包含完整的通用研究流程。

### 让 AI 先理解你要的结果

当你只说“研究一下这个库”时，`interview-me` 可帮助澄清研究是为了学习、选型、二次开发还是部署。若问题已经像本次一样明确，则可以直接研究，无需额外进行一轮访谈。

`idea-refine` 更适合下一步：“了解这个库后，我能用它做什么？”它可以帮助比较多个应用方向，并把选定方向收敛成一页方案。

### 减少大任务的遗漏

`planning-and-task-breakdown` 可借鉴为研究任务清单：定位 → 能力 → 场景 → 原理 → 局限 → 个人价值 → 验证。每一步定义产出，便于检查是否完整。

`source-driven-development` 的原生用途是依据框架官方文档实施代码。当前可借鉴其“固定版本、优先一手来源、明确未验证项”的方法，但通用资料检索仍需要单独设计研究规范。

## 3. 建议优先级

| 优先级 | 技能或方法 | 对你何时有价值 |
| --- | --- | --- |
| 当前优先借鉴 | context-engineering、documentation-and-adrs | 管理多个研究子项目，保存背景、依据和决策。 |
| 需求不清时使用 | interview-me、idea-refine、planning-and-task-breakdown | 明确研究目的、比较应用方向、安排复杂工作。 |
| 做演示时采用 | spec-driven-development、incremental-implementation、frontend-ui-engineering、test-driven-development、browser-testing-with-devtools | 从研究进入可运行的页面或应用。 |
| 维护代码时采用 | debugging-and-error-recovery、code-review-and-quality、git-workflow-and-versioning、code-simplification | 处理缺陷、检查变更、保留回退点。 |
| 出现相应需求再采用 | constraints、API、安全、性能、CI/CD、监控、迁移和发布相关技能 | 当你确实有接口契约、用户数据、性能指标或上线任务。 |
| 谨慎按需使用 | doubt-driven-development | 对高代价或难核验的判断做独立复核；评估新增耗时与工具前提。 |

表中的 `constraints` 指 `constraint-driven-development`。这是本次个人化采用建议，不是上游宣称的优先级。

## 4. 三个具体使用例子

**继续研究一个开源库**

示例请求：“先读取本项目的研究记录，沿用已确定的问题和证据口径，核查上游固定版本；按能力、场景、限制与对我的价值更新研究文档，并标明未实测内容。”

可借鉴上下文管理与决策记录；不需要调用测试驱动或生产发布流程。

**把研究成果做成可交互演示**

示例请求：“根据研究文档，先明确演示的目标用户、三个核心操作和验收条件，再按可运行的小步骤实施；完成后检查真实浏览器中的操作和响应式布局。”

适合规格、计划、增量实现、UI 工程和浏览器验证。前提是有代码环境与相应浏览器工具；安装技能不会自动补齐所有依赖。

**让 AI 修复演示中的错误**

示例请求：“先复现搜索结果错误的问题，保存失败证据，定位原因后做最小修复，补充能防止复发的验证，最后检查相关功能是否受到影响。”

适合排错、测试与审查。你应查看“如何复现、改了哪里、验证了什么”，而非只接受“已经修好”的结论。

## 5. 一次小规模试用怎样判断效果

建议选择两个规模相近的真实任务：一个沿用当前方式，一个显式引入少量相关技能。固定模型、工具权限与项目背景，记录下列信息。单次比较只能作为线索，不能证明普遍效果。

| 观察项 | 记录方式 |
| --- | --- |
| 需求覆盖 | 列出验收项，看最终完成了几项。 |
| 事实与来源 | 抽查关键判断是否有匹配版本的一手证据。 |
| 返工 | 记录你纠正理解、补充要求和修复错误的次数。 |
| 交付可用性 | 检查文档链接，或实际执行产品的核心操作。 |
| 交互成本 | 记录总耗时、额外问答轮次；有数据时记录模型用量。 |
| 可继续性 | 新会话能否仅凭项目文件正确接续任务。 |

观察到反复确认、无关检查或文档膨胀时，应缩小所用技能范围。技能选得更少且与任务相符，通常比机械加载全部技能更值得优先尝试；实际收益仍需测量。

## 6. 最值得沉淀的个人扩展

结合你现有仓库，可以在未来创建一个专门的“开源项目研究”技能，固定如下步骤：

1. 检查现有项目与历史编号，避免重复收录。
2. 记录上游地址、版本、许可证和研究目的。
3. 区分作者声明、源码或文档核验、实际运行、个人推断。
4. 逐项整理能力、输入输出、适用场景、前提和限制。
5. 结合已知个人目标判断价值，未知背景明确标注。
6. 将报告、清单和证据写入子项目，更新总索引。
7. 只有研究问题需要时，再制作演示或进行安装测试。

这是建议的后续扩展，本次没有创建或安装该技能，也没有对当前 AI 助手的全局配置作更改。
