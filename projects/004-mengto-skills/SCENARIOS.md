# MengTo/Skills · 使用场景与预期效果

本页把技能组合成可理解的任务。每个场景的产出是采用后的目标，不是本次已经制作的成果。技能原文与逐项解释见 [完整索引](SKILLS.md)；通常先用一个主技能，有具体缺口再补充其他技能。

## 1. 看到了一个喜欢的网站，但说不清它为什么好

**输入：** 可访问的网站、录屏、截图或 HTML，以及想借鉴的部分。

**选择：** 录屏用 `video-to-superprompt`；已有 HTML 用 `html-to-interaction-prompts`；页面截屏不完整时补 `stitched-full-page-capture`。

**目标产出：** 页面结构、字体与颜色关系、动画时序、滚动行为、素材清单，以及可用于实现的说明。结果可以帮助你区分“喜欢整体风格”和“只需要某个交互”。

**验收：** 每个重要描述能对应实际参考；不把看不到的状态当成事实；动态效果说明触发方式与结束状态；移动端与低动效方案有明确安排。

**边界：** 视频无法单独证明原始代码、后端能力或所有交互。分析得到的技术选型是重建建议，应与直接观察区分。

## 2. 把一个研究子项目变成清楚的介绍页面

**输入：** 已完成的研究结论、真实功能、面向谁、希望读者执行什么动作。

**选择：** 先用 `design-first-ui-prompting` 明确要求，再选择 `landing-page` 或 `product-proof-saas`。需要演示某个真实操作时，再补对应交互技能。

**目标产出：** 页面结构、主文案、产品或项目示例、能力边界与入口；适合做本研究集未来的项目展示页。

**验收：** 读者能快速回答“是什么、能做什么、证据在哪里、下一步怎么用”；说明与真实项目相符；示例数据有标识；链接、手机排版和键盘操作可用。

**边界：** 页面中的预约、价格、审批或安全介绍不代表后端系统已经实现。以界面演示代替真实服务时，应明确标注。

## 3. 做个人作品集或品牌展示

**输入：** 作品、品牌内容、图片、目标受众与风格参考。

**选择：** `editorial-portfolio-chapters` 或 `build-awwwards-quality-sites` 作为主流程，再选择一套相容的风格。不要同时加载深色玻璃、纸感、粗野风格等互相冲突的整套规范。

**目标产出：** 视觉统一的页面、重点作品章节、联系入口，以及有节奏的过渡。

**验收：** 作品比装饰更突出；视觉风格统一；实际图片加载正常；动效不会阻止阅读或点击；缺少 WebGL 或减少动画时仍有完整内容。

**边界：** 获奖与商业表现不能由风格名称推断。没有真实客户、评价或指标时不应自行补造。

## 4. 给已有页面加一个特定交互

**输入：** 现有代码、目标位置、希望改变的行为和保留内容。

**选择：** 流程进度用 `scroll-progress-timeline`；产品旋转或装配讲解用 `scroll-scrubbed-visual-sequence`；材质对比用 `reveal-hover-effect`；真实处理状态可用 `thinking-orbs` 或 `beam-glow-states`。

**目标产出：** 聚焦一个任务的小型交互，保持已有页面的内容与视觉系统。

**验收：** 鼠标、触控与键盘下的主要任务都成立；前进、返回与重新进入行为正确；状态反馈与真实业务状态一致；离开页面后没有多余动画循环。

**边界：** 装饰性效果应有明确作用。不能把一个加载动画当成异步任务已经正确完成的证据。

## 5. 制作三维展厅、环境或产品展示

**输入：** 模型与材质、目标设备、相机方式、加载与性能预算。

**选择：** 基础整合用 `threejs`；导览用 `3d-virtual-tour`；环境按需选天空、四季或海洋；章节式空间故事用 `build-threejs-scroll-worlds`。

**目标产出：** 可探索或可按章节观看的三维场景，带资源加载和静态替代方案。

**验收：** 目标设备实测加载耗时、帧耗时与内存；相机不会穿越不应进入的位置；控制可以恢复；低质量模式保持信息完整；隐藏页面时适当暂停。

**边界：** 增加模型面数和渲染分辨率会增加资源成本，不能假设所有设备都能流畅显示。素材制作和来源处理仍是项目工作的一部分。

## 6. 做一个能玩的浏览器游戏原型

**输入：** 一个小而明确的玩法、目标设备、角色或敌人素材、完成条件。

**选择：** 从 `build-isometric-arpg` 的小循环开始，再按需要补战斗、敌人、背包等技能，最后用 `test-playable-web-games` 验收。

**目标产出：** 移动、一次战斗、奖励、失败重试和继续游戏组成的可玩切片。

**验收：** 能从开始走到结束；命中与伤害一致；奖励不丢失；存档和重试可靠；目标输入设备可操作；浏览器实际试玩无关键阻断。

**边界：** 一次构建成功不等于游戏可玩。完整商业游戏的内容量、平衡、资产和维护远超技能目录本身。

## 7. 页面能用了，但看起来重复、杂乱或不可信

**输入：** 真实页面或截图、主要用户任务、当前设计系统。

**选择：** `audit-ai-design-slop` 适合只审查；`no-ai-design-slop` 适合在修改时持续检查。只有明确需要数字质量目标时，才采用 `workflow-score-to-target`。

**目标产出：** 按影响排序的删改建议或修正后的页面，指出证据、问题和收益。

**验收：** 每个发现有具体位置；不因单独使用渐变、玻璃或卡片就判定低质；修正后任务更清楚；前后使用相同视口和状态比较。

**边界：** 审查不能判断作品一定由 AI 制作；评分属于基于标准的判断，不是绝对事实。

## 8. 将一次成功制作变成长期可用的经验

**输入：** 已验证的代码、效果、失败记录及相关来源。

**选择：** 现有成品用 `web-technique-to-skill`；教程或提示包用 `article-prompts-to-skills`。

**目标产出：** 明确适用条件、关键机制、参数、示例、限制和验收方法的个人技能。

**验收：** 更换主题和配色后核心方法仍成立；没有依赖原项目的私有路径；示例能证明其声称的机制；文档保留原项目中真正重要的坑点。

**边界：** 未经过实际使用的设想不应包装成已验证经验。个人品牌和第三方素材也不应无差别复制到通用模板。

## 一张表选择下一步

| 当前情况 | 优先做什么 | 可以期待的成果 |
| :--- | :--- | :--- |
| 还在研究库本身 | 阅读本项目，不必安装全部技能 | 知道选什么、什么时候选 |
| 已有参考但缺少说明 | 提取结构与交互要求 | 可交付给开发的设计说明 |
| 已有内容但没有展示页 | 明确页面目标与信息结构 | 内容可信、重点清楚的页面原型 |
| 已有页面但局部欠缺 | 只加入解决缺口的技能 | 一个可验证的小改进 |
| 需要三维或游戏体验 | 先定义小范围完成条件与设备 | 可运行且有证据的原型 |
| 同类任务已重复发生 | 提炼实际有效的方法 | 自己维护的技能与参考库 |
