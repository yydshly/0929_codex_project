总览

先读摘要：QM 能做什么，何时与你有关

QM 是以 Agent 执行为核心的工作平台。执行引擎负责推进任务，QM 把资源、协作与持续工作组织起来。

01 / 库的能力

把 Agent 放进可持续工作的环境

通过 Codex、Pi 等引擎调用模型和工具，处理资料、文件与代码；再统一组织个人和项目空间、记忆、Skills、权限、定时与事件任务，以及成果发布。

02 / 可实现的效果

从对话走向可检查的成果

可以形成仓库变化报告、代码改动与测试记录、邮件草稿、项目进展清单、共享文件或内部看板。具体效果取决于接入的工具、数据、授权及验收要求。

03 / 使用场景

研究、开发、团队与信息工作

持续研究开源项目、维护代码库、汇总团队进度、整理文档与邮件，或制作需要持续更新的内部工具。

04 / 对我们的意义

让研究方法和项目知识持续积累

现在借它看懂 Agent 产品架构；以后把“研究项目 → 按模板整理 → 更新网页 → 持续跟踪”连接成可重复、可共享的工作流程。

05 / 什么时候用

有持续运行与协作需求时再采用

个人临时研究、写网页，现有 Codex 足够时不必急着迁移。需要定期跟踪多个项目、主动提醒，或多人共享且凭据分开管理时，再评估 QM。

与 Codex 的关系：执行条件相当时，可承接同类任务。

例如研究仓库、修改代码、制作网页、运行测试。文件、工具、插件、权限和运行环境仍需在 QM 中准备；接入引擎不会自动继承你在 Codex 应用里的全部任务与配置，也不保证执行效果完全一致。

02

原理：先确定工作空间，再执行任务

QM 的重要设计是 Scope（空间 / 作用域）：资源有归属，操作有身份，结果有受众。执行引擎在这个边界内调用模型和工具。

01 / 工作边界

你的私人研究助理

整理我正在关注的开源项目
记忆个人研究偏好与笔记
文件个人收集的材料与草稿
凭据个人获准使用的服务
任务属于个人空间的跟踪计划

默认 Isolated：资源留在所属空间，跨空间共享需要明确授权。

06

对你的意义：什么时候值得用 QM

基于你目前的“研究开源项目 → 整理能力 → 制作展示 → 积累方法”工作方式，价值判断需要区分现在与未来。以下是本研究的建议。

现在 / 看懂产品层次

辨别工作台真正增加了什么

模型、执行引擎、Skill 和协作平台分别解决不同问题。QM 值得研究的是资源归属、授权、持续任务与成果交付如何成为一套产品。

下一步 / 持续研究

让知识跟着项目更新

如果你需要很多仓库长期跟踪、共享研究材料、按固定方法定期产出，QM 的空间、记忆、技能与调度组合会更有意义。

以后 / 团队与自建产品

复用完整工作环境的设计

有多人协作、不同服务凭据和共享应用时，可以评估完整部署；若自建 Agent 产品，也可参考其接口与资源管理方式。

当前判断：先作为产品架构参考，以一个真实需求决定是否试用。

如果主要是个人临时研究和生成网页，现有工具已能完成任务，迁移收益可能有限。出现“需要持续运行、成员共享、凭据分开管理”的明确需求时，再用一个低风险的仓库跟踪场景检验 QM。

试用时应核对：输出是否可靠、空间共享是否符合预期、重启后任务能否继续，以及模型调用与基础设施的实际费用。

现在 · 学习参考个人临时任务

现有工具已经够用，先理解架构与工作方式。

下一步 · 小范围试用长期跟踪与定期交付

需要离线继续执行、定期更新资料或主动提醒。

以后 · 评估正式采用多人、分权与共享应用

成员需要共同使用 Agent，资源和凭据有不同归属。

第一个试点：一个仓库的每周变化报告。 准备公开仓库、固定研究模板和获准的交付位置；用定时任务检查更新，生成带来源的差异摘要。核对报告质量、授权边界、重启恢复与实际费用，再决定是否扩大范围。这是建议方案，本次未部署实测。

边界需要怎样理解

上游明确标注早期实验性质，目标是组织内部认证用户，不能直接理解成经过加固的公共多租户平台。审批、隔离和审计有实现，也有部署相关的限制。

后台任务不保证结果质量；多 Agent 不自动保证更快、更便宜；换引擎不保证行为一致。个人资料是否共享取决于具体授权与共享策略。
