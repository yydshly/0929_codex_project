## 实际核查结果

| 核查项 | 操作与结果 | 对结论的影响 |
| --- | --- | --- |
| 固定版本 | GitHub commits/main 返回上述 SHA，再读取对应文件 | 避免研究依据随 main 变化 |
| 仓库范围 | 完整树 `truncated=false`，581 个 blob | 文件检索未因分页截断漏掉条目 |
| 后端与权重 | 检索 `.py/.onnx/.pt/.pth/.ckpt/.safetensors` 没有匹配 | 不能从此 Git 树复原具体视频网络；不代表镜像内部也没有 |
| 标准服务 | Windows/Linux Compose 均包含 TTS、ASR、视频服务 | 支持本地服务组合的结论 |
| 配置变体 | Lite 一个服务；5090 两个服务 | 不统一假定所有版本有三项服务 |
| 正式与开发地址 | 正式为回环地址，开发为特定局域网 IP | 补充“默认本地”适用条件 |
| 开发样例 | 人物处理与视频生成有写死测试素材的开发分支 | 直接启动开发模式不能证明真实端到端可用 |
| 人物创建 | 视频转码、提音频、请求声音处理、写素材记录 | 不将“新增模特”直接解释成个人权重训练 |
| 新视频生成 | 已有音频或 TTS 二选一，再请求视频服务 | 确认两种主要输入流程 |
| 队列 | waiting/pending 状态与约两秒轮询 | 排队能力可见；吞吐与可靠性未测 |
| 音视频资源 | 找到 Windows/Linux FFmpeg/FFprobe 路径与打包配置 | 整理二进制依赖，不只列 JS 包 |
| 授权描述 | README 与 LICENSE 的阈值不同 | 商业集成必须先明确条款；不下“无限制免费”结论 |

## 仍待回答的问题

1. 视频服务具体的模型结构、参数量、训练方法及权重来源是什么？
2. 不同镜像的版本、依赖、许可证与可重复构建方式是什么？
3. 50 系列配置里的参考音频识别如何实现？
4. 目标机器的最低可用显存、峰值内存、每分钟视频耗时是多少？
5. 长音频和原视频长度不同、较大转头、复杂口型时如何处理？
6. 断网后的全部功能是否正常，是否存在额外下载或网络行为？
7. 商用时根 LICENSE、模型协议 PDF 与 README 如何适用？

这些问题不妨碍描述已确认的应用链路，但影响部署、算法研究深度与商业采用。
