## 仓库能力如何成立

### 1. 入口描述帮助识别任务

每项技能使用 `SKILL.md` 作为入口，其中名称、描述用于告诉宿主“什么时候读取这份规则”。正文规定如何工作。相邻参考文档给出具体配方、检查表和代码模式。

当前 11 项中，`interface-review`、`explain-interface`、`break` 和 `variant` 声明为用户主动调用。源码同时使用 Markdown frontmatter 与 `agents/openai.yaml` 表达相应宿主策略。其余技能可以作为领域规则被流程调用。这里描述的是上游配置意图，实际加载行为还取决于宿主版本与支持情况。

### 2. 知识与流程分工

六个领域技能维护各自规则；`better-interface` 管理跨领域排序和报告；`interface-review` 管理变更范围及问题分类；另外三个工作流分别负责解释、场景观察与方案探索。

例如“文字被截断”可以涉及三个领域：原句是否过长属于文案；断行或截断实现属于排版；容器是否给足空间属于布局。一个根因不应在三个报告中重复出现。

### 3. 模型解释规则，宿主执行动作

典型链路是：用户请求 → 识别技能 → 阅读入口与相关参考 → 理解项目 → 读取代码或操作浏览器 → 形成报告或修改 → 验证指定结果。

这是由自然语言规则驱动的工作过程。仓库没有独立构建、lint 或测试工具，不会自行扫描项目，也不因安装而改变模型参数。实际能力需要模型理解、文件工具、Git、浏览器与项目预览配合。

| 宿主具备的条件 | 可以支持的工作 | 仍无法据此保证的事 |
| --- | --- | --- |
| 文件读取 | 源码、文案、变量与规则检查 | 页面实际如何渲染 |
| Git 与版本访问 | 对比变更、追踪删除与使用方 | 交互运行后一定正常 |
| 写文件与项目运行 | 实施修复、生成场景页和候选 | 页面已经经过人工或自动观察 |
| 浏览器与样式读取 | 检查布局、实际颜色、动画和状态 | 所有浏览器和设备都覆盖 |
| 键盘、辅助技术与目标设备 | 更完整地验证操作和播报 | 一次测试证明全部标准或所有用户情境 |

### 4. 明确证据与输出约定

上游整体审查要求关联文件位置、报告检查覆盖、按根因合并、区分未检查与没有发现问题。解释技能区分实测、推导和推断。颜色技能要求测量，不允许凭外观估一个对比度。

这些约定有助于让 AI 的结论可复查，但它们依然是需要模型遵守的指令，未成为强制执行的校验程序。

## 能力边界中的重要细节

- **审查不等于修复。** better-interface 与各领域审查默认输出发现；用户提出修复任务后才落实代码。
- **整体审查不等于变更审查。** interface-review 必须解析基线，检查删除部分并分类问题。
- **场景页不等于回归套件。** break 是一次性的轻量构建和观察，当前规则不要求完整自动化。
- **可运行候选不等于正式方案。** variant 需要用户选择，之后收敛和清理临时结构。
- **解释不等于源码恢复。** explain-interface 当前正文强调文字配方，不应把推测复刻当成原作者实现。
- **配方不等于通用标准。** 圆角、动画数值、间距等包含作者设计经验，需要结合目标产品判断。
- **源码证据与运行证据不同。** 没有浏览器时仍可检查许多代码问题，但不能伪称已经观察到视觉结果。

## 可扩展方向

以下为本研究建议，不是当前仓库已经实现的能力。

| 方向 | 具体扩展 | 可增加的效果 | 成本与验收方式 |
| --- | --- | --- | --- |
| 团队设计规则 | 给领域技能增加团队颜色、组件、字号、密度与术语约定，并说明例外 | 改法更符合自己的产品 | 先用现有页面试审，检查是否误报有意设计 |
| 可计算检查 | 增加颜色计算、无障碍扫描、溢出探测等工具接口 | 把部分文字规则落实为可重复结果 | 记录工具版本、输入和输出，人工核对误报 |
| 持续组件回归 | 把 break 中有价值的场景转为长期样例与自动化用例 | 后续修改时能复现已知边界问题 | 需要维护测试数据、截图基线和环境 |
| 中文与多语言 | 增补 CJK 字体回退、标点、混排、翻译膨胀和语言专属例外 | 提升非英文界面的适用性 | 使用真实语言样例及目标设备验证 |
| 专业组件 | 增加表格、图表、权限、复杂筛选与表单规则 | 扩展到高密度业务产品 | 规定清晰责任领域，避免复制已有通用规则 |
| 评估样例库 | 建立已知错误、正确实现和等效重构样例 | 测量漏报、误报和修复成功率 | 按版本重复运行，记录人工判定依据 |
| PR 流程集成 | 在变更流程接入界面审查并保存报告与渲染证据 | 团队每次交付都能查看可追溯结果 | 需要隔离预览、适当权限、耗时预算与结果存储 |
| 结构化报告 | 增加 JSON 输出字段、稳定问题标识和来源位置 | 便于搜索、统计与跟踪同一根因 | 校验格式，仍需对结论真实性做抽查 |

建议先补团队规则，再增加可测量工具，最后沉淀回归与评估样例。仅增加更多 Markdown 规则可能扩大覆盖，但不能自动提高判断可靠性。

1. 阅读本地子项目收录规范，发现编号 005 已分配，因此使用 006。

5. 整理六个使用场景、技能责任边界、原理与扩展方向。
6. 检查技能覆盖、调用配置、来源 SHA-256 与研究文档本地链接，并保存验证结果。

没有把上游 AGENTS.md 或 SKILL.md 当作本次工作区的执行指令；这些文件是被分析的研究材料。

## 已得到与未得到的结论

**已得到：** 当前固定版本包括六个领域技能和五个流程技能；文档能指导报告、修复、场景页、候选方案及实现解释；具体效果与边界已逐项说明。

**未得到：** 技能实际运行成功率、不同模型的一致性、修复质量、审查耗时、用户体验或商业指标改善。这些都需要单独的运行实验。
