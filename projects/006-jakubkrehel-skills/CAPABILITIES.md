**证据说明：** 以下是对上游工作规范的中文整理；“效果”指按规范执行并通过验证后可以达到的目标。“前后示例”均为本研究构造，未运行上游技能，不能作为实测成绩。审查请求通常只交付报告；需要代码变化时，应明确要求实施修复。

<a id="better-interface"></a>
## 1. better-interface · 跨领域界面审查

**职责：** 组织六个领域技能，形成一份按用户影响排序的报告。适合页面、功能或完整流程审查。

**需要提供：** 页面或流程范围、可读的项目代码；涉及视觉和运行行为时，还需要可访问的预览与相应工具。

| 具体能力 | 如何执行 | 可实现效果 |
| --- | --- | --- |
| 确定范围 | 从任务定位页面、流程或仓库；范围过大时收敛到一条完整流程并写明排除项 | 用户知道哪些内容已查、哪些尚未覆盖 |
| 理解项目约束 | 查看框架、样式体系、组件库、设计变量、项目规范和预览命令 | 改法能融入现有项目，不凭空引入另一套设计系统 |
| 按基础优先审查 | 依次检查无障碍、布局、文案、排版、颜色、UI 细节 | 操作障碍不会被圆角、阴影等细节掩盖 |
| 检查状态 | 覆盖范围中实际存在的空、加载、错误和窄屏状态 | 不只评价“有数据且加载成功”的页面 |
| 用证据定位问题 | 关联文件和行号；视觉判断需要对应渲染证据 | 每个问题能够追溯到实现位置和实际表现 |
| 统一优先级 | 以 HIGH、MEDIUM、LOW 评价用户影响；按影响范围继续排序 | 先解决任务阻断和共享组件问题 |
| 合并根因 | 同一变量或组件造成多个位置出错时合并为一条 | 避免十处相同错误变成十项重复工作 |
| 优先选择低成本修复 | 先考虑删除多余内容、采用原生能力、复用已有规则，再考虑新增 | 降低修复引入的维护负担 |
| 明示不确定性 | 未加载领域记为 Not reviewed，未完成检查记为 Not verified | 不把没有检查当成通过 |

**交付物：** 范围说明、六领域覆盖表、通常最多 15 条的合并发现、验证记录、结论。报告上限不应掩盖阻断问题；超出时需说明。用户另外要求修复后，才落实相应改动并重验。

**前后示例：** 一个设置页面同时存在键盘无法关闭弹窗、错误提示无恢复动作、标题换行失衡。输出按影响排序的三类发现，定位各自代码；多个弹窗共用同一焦点实现时，优先修复共同组件。

**验收重点：** 每条发现有位置、当前表现、改法和原因；覆盖表如实反映实际检查；未运行的步骤不能写成通过。

**边界：** 它不负责解释 Git 变更范围，也不自动启动用户专用的 `interface-review`；缺少某个领域技能时只能完成部分审查。

**示例请求：** “使用 better-interface 审查账户设置流程，覆盖加载、错误和手机宽度，给出问题证据与修复优先级。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-interface/SKILL.md) · [报告规范快照](sources/skills/better-interface/review-format.md)

<a id="better-ui"></a>
## 2. better-ui · UI 细节与动效

**职责：** 在基础交互正确的前提下，改善表面层次、图标、视觉对齐和动画反馈。保留项目已有的组件、变量与信息密度。

**需要提供：** 待优化组件、样式代码和现有动效库信息；确认视觉效果需要浏览器。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 嵌套圆角协调 | 按外圆角、内圆角和内边距的关系检查嵌套表面 | 卡片内部图片和容器边缘更协调 |
| 视觉对齐 | 对播放三角形、非对称图标等做光学位置修正 | 避免数学居中但肉眼偏移 |
| 区分结构与层次 | 结构、选中与焦点保留边框；深度可使用多层透明阴影 | 表面层次清楚，减少无意义分隔 |
| 可打断的状态过渡 | 交互状态优先使用 transition；单次分段序列再用关键帧 | 快速移入移出或重复操作时反馈更连贯 |
| 入场与退出节奏 | 低频分段入场可交错；退出使用轻微位移 | 顺序帮助理解层级，离场不过分抢注意力 |
| 图标状态切换 | 组合透明度、缩放和模糊；按项目是否已有 Motion 选择实现 | 复制成功、收藏切换等状态变化更平滑 |
| 按压反馈 | 上游指定按压缩放 0.96，并允许静态模式关闭 | 点击有即时反馈，也能在不适合动效时停用 |
| 切换主题处理 | 主题切换期间临时抑制大范围过渡 | 避免整页颜色、边框和阴影同时拖影 |
| 限定动画属性 | 明确声明变化属性，谨慎添加 will-change | 减少意外动画与过早优化 |
| 图标体系一致 | 使用 currentColor，根据文字重量调整线条粗细 | 图标与文字更协调，状态换色无需多份图片 |
| 控制动效频率 | 高频操作保持即时或短过渡，并保留文字或图标状态 | 反复操作不拖沓，关闭动画后仍能看懂结果 |

**交付物：** 细节问题与修改建议；要求实现时可得到 CSS、Tailwind 或现有动效库的改动，以及组件状态检查记录。

**前后示例：** 复制按钮原先直接替换图标，图标大小跳动；改为同位置切换并显示“已复制”，既能看出过渡，也能在动画结束后判断状态。

**验收重点：** 检查 hover、focus、active、loading 等实际状态；需要时降低动画播放速度观察跳变；检验主题切换。

**边界：** 某些数值是作者指定的设计配方，并非通用标准或实测最优值。可访问名称、键盘支持与减少动态效果要求由 `better-accessibility` 负责。

**示例请求：** “使用 better-ui 改善复制按钮的图标切换和按压反馈，沿用现有变量，保留静态状态提示。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-ui/SKILL.md) · [动效配方](sources/skills/better-ui/animations.md) · [图标切换](sources/skills/better-ui/icon-transitions.md)

## 3. better-typography · 字体与文字排版

**职责：** 管理文字如何显示、换行、对齐和适应内容长度；文字具体说什么由 `better-writing` 负责。

**需要提供：** 页面或组件、真实长度的文案、字体资源和现有字号变量。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 字体格式与真实字形 | 使用合适的网页字体格式，确认实际加载了所需字重与斜体 | 减少浏览器合成字形造成的视觉偏差 |
| 可变字体设置 | 优先用 font-weight、font-optical-sizing 等属性，特殊轴再用底层标签 | 设置更易理解，回退字体行为更合理 |
| 字号系统 | 建立少量语义字号，检查标题视觉层级 | 页面重点清楚，组件不各自随意定字号 |
| 行高与文字长度 | 根据标题、正文和多行说明分别处理行高与行宽 | 多行文本更易读，减少拥挤和过长阅读行 |
| 标题与描述换行 | 按角色使用 balance、pretty 等方式，处理长 URL 和标识符 | 标题更均衡，长内容不轻易撑破容器 |
| 动态数字稳定 | 计数器、价格与计时使用 tabular-nums | 数字变化时列宽和对齐更稳定 |
| 截断可恢复 | 单行或多行截断时，为重要内容保留完整查看方式 | 节省空间的同时不永久丢失信息 |
| 文本装饰 | 调整下划线位置与厚度，区分说明性提示 | 链接和注释提示更清楚 |
| 移动输入框 | 针对小字号输入框的移动浏览器缩放问题提供适配方案 | 输入时更容易保持预期页面尺度；仍需真机验证 |
| 语言和混合方向 | 设置 lang、dir，必要时使用 bdi 隔离动态内容 | 混排标点、名称与数字顺序更可靠 |
| 文本可选择性 | 默认保留复制选择能力，仅在拖拽等冲突场景限制 | 用户可以复制订单号、名称等有用信息 |

**交付物：** 字体与排版问题清单、字号与样式建议；要求修复时交付对应规则和必要的完整文本查看方式。

**前后示例：** 表格价格从“111”变为“888”时视觉跳动，商品名被截断后无法查看。修复后数字列稳定，长名称可展开，窄屏下能合理换行。

**验收重点：** 使用真实长短文案调整宽度；检查标题层级、字重资源、多行文本、数字更新与截断恢复。

**边界：** 字体回退和排版必须结合目标语言与设备确认。上游的行长、字距等经验不应未经验证直接转成中文排版的统一标准。

**示例请求：** “使用 better-typography 修复订单表格的数字跳动与长名称截断，保留紧凑布局并支持查看完整名称。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-typography/SKILL.md) · [CSS 对照](sources/skills/better-typography/css-cheat-sheet.md) · [字体特性](sources/skills/better-typography/variable-fonts-and-opentype.md)

## 4. better-colors · 颜色系统与测量

**职责：** 从单个颜色扩展到色阶、语义、主题和实际渲染对比度，减少“今天这个值看起来正好”的偶然依赖。

**需要提供：** 品牌或强调色、现有颜色变量、组件使用位置、主题模式；精确结果需要颜色计算和渲染证据。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 适配现有表示法 | 复用项目已有 hex 等格式；新系统可采用 OKLCH | 避免为了修复一处而增加混乱的表示体系 |
| 按职责设计色阶 | 围绕背景、悬停、边框、实体填充和文字建立必要色阶 | 每个颜色有用途，不生成无人使用的庞大色板 |
| 分离原始与语义变量 | 原始变量表达色值，组件使用表达用途的语义变量 | 修改品牌和深色模式时，更容易维持语义关系 |
| 避免借用变量 | 文字使用文字变量，分隔线使用分隔线变量 | 后续修改边框色不会意外让文字变淡 |
| 构造感知色阶 | 用颜色计算库处理感知明度、色相与鲜艳程度 | 获得更连贯的色阶，降低纯目测调色的不确定性 |
| 控制颜色含义 | 检查强调、危险、状态色是否冲突，区分主次动作 | 用户更容易识别主要操作和危险后果 |
| 测量实际前背景 | 考虑卡片背景、透明度、混合色和图片背景 | 对比度报告能反映实际使用位置 |
| 主题和色域检查 | 检查明暗主题、显示色域及回退色 | 避免某主题通过、另一主题失败 |
| 渐变空间选择 | 解释不同插值空间对中间色和明度的影响 | 根据想要的视觉效果选择渐变方式 |
| 修复后重算 | 需要修复时优先调整合适的明度等参数，并再次测量 | 不能只凭“看起来更深了”宣布问题解决 |

**交付物：** 颜色变量映射、色阶方案、颜色对与测量值、失败阈值及修复建议。审查中不主动重涂配色；用户明确要求修改后实施并复测。

**前后示例：** 次级文字误用了分隔线变量，导致深色模式下阅读困难。修改后增加或复用正确的文字语义变量，分别记录两种主题下的真实颜色对和测量结果。

**验收重点：** 记录工具、前景、实际背景、主题和结果；透明表面或图片上的文字需要考虑不同背景区域。

**边界：** 上游参考同时讨论 WCAG 2 对比度与 APCA。两者应清楚区分，不能把一个指标的通过结果当作另一套要求的通过。这里未独立核验上游所有数值配方。

**示例请求：** “使用 better-colors 梳理明暗主题中的文字与边框变量，测量失败的颜色对，并在保持品牌色的前提下修复。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-colors/SKILL.md) · [测量方法](sources/skills/better-colors/contrast.md) · [变量命名](sources/skills/better-colors/token-naming.md)

<a id="better-accessibility"></a>
## 5. better-accessibility · 可操作与可感知的界面

**职责：** 检查用户通过键盘、辅助技术、触摸及不同显示偏好能否理解和完成任务。

**需要提供：** 一条明确流程、控件源码、目标浏览器及辅助技术环境；动态交互需要实际操作确认。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 使用正确原生元素 | 动作用 button、导航用带地址的 a，减少不必要的 ARIA | 获得原生键盘行为及链接打开方式 |
| 控件可访问名称 | 输入框绑定 label，纯图标按钮提供描述性名称 | 辅助技术能识别控件用途 |
| 可见焦点 | 检查 focus-visible，验证自定义指示器与邻近背景 | 用户能知道键盘当前操作哪个控件 |
| 完整键盘路径 | 检查 Tab、Enter、Space、Escape 和复合控件方向键 | 不依靠鼠标也能完成主要流程 |
| 弹窗焦点管理 | 打开时移入焦点，约束背景操作，关闭后返回触发处 | 操作不误入被覆盖页面，关闭后能继续原任务 |
| 点击区域 | 检查目标大小、间距与扩大后的碰撞，装饰层不拦截事件 | 小图标更容易点击，邻近控件不互抢点击 |
| 表单输入支持 | 配置 type、inputmode、autocomplete，保留粘贴 | 使用合适键盘并允许密码、验证码等输入方式 |
| 表单错误关联 | 将错误与字段关联，标明无效状态，聚焦首个错误 | 用户能定位错误并知道修改哪里 |
| 动态内容播报 | 按场景选择描述关联、普通状态播报或紧急警告 | 搜索结果、保存结果等变化可被感知 |
| 多通道状态表达 | 颜色之外增加文本或图标 | 不仅依靠红绿颜色判断成功和失败 |
| 动效偏好 | 尊重减少动态效果设置，处理自动播放和重要通知 | 对动态效果敏感的用户仍能使用流程 |
| 图片与页面结构 | 按用途处理 alt、标题层级、主区域和跳转正文 | 便于理解图片作用和按结构导航 |
| 缩放与窄屏 | 检查文本放大、200% 缩放与 320px 重排 | 放大阅读时不丢失内容与操作 |

**交付物：** 障碍清单、对应代码位置与修复方向、键盘和辅助技术检查记录；要求实施时交付语义和交互修复。

**前后示例：** 弹窗只有一个没有名称的关闭图标，Tab 能进入背景。修复后按钮具备名称，键盘留在弹窗内，Escape 可关闭，焦点返回打开按钮。

**验收重点：** 完整走一遍键盘流程；检查可访问名称、角色与状态；必要时使用目标屏幕阅读器。源码检查或自动扫描不能替代所有实际操作。

**边界：** 技能给出规范和检查流程，本次没有执行合规审计；采用技能本身不能构成整站合规证明。颜色测量交给 `better-colors`。

**示例请求：** “使用 better-accessibility 修复登录弹窗的键盘路径、焦点返回和错误播报，并列出实际验证过的步骤。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-accessibility/SKILL.md) · [表单](sources/skills/better-accessibility/forms.md) · [焦点与键盘](sources/skills/better-accessibility/focus-and-keyboard.md)

## 6. better-layout · 布局与内容适应

**职责：** 用位置、间距、对齐和阅读顺序表达信息关系，并让内容在宽度、语言和数量变化时保持可用。

**需要提供：** 页面结构、支持的尺寸、真实内容及翻译场景、项目间距与密度规范。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 空间分组 | 优先用间距表达组内与组间关系，再考虑背景和分隔线 | 用户更容易理解字段或内容的归属 |
| 共同对齐边 | 控制标题、内容和操作的对齐与层级缩进 | 减少视觉噪声，形成可扫描的结构 |
| 控件与内容区分 | 为交互元素提供背景、边界或一致的位置区域 | 用户更容易看出哪里可以操作 |
| 按重要性排序 | 重要内容靠前，并按语言阅读方向组织 | 核心内容和主要操作更容易被发现 |
| 隐藏内容提示 | 对横向滚动、折叠和逐步展开提供可见线索 | 用户能发现屏幕之外还有内容 |
| 控件间距 | 结合已有密度、点击区域和邻近控件安排间距 | 紧凑界面中仍能区分操作且减少误触 |
| 边缘与安全区 | 内容可延伸到边缘，文字和控件考虑页边距与安全区 | 重要按钮不与系统区域冲突 |
| 内容驱动断点 | 在内容真正放不下时折叠，组件级适配可使用容器查询 | 相同组件嵌入侧栏或主区都能合理调整 |
| 翻译与长内容 | 避免按一种语言定死文字容器尺寸，测试伪本地化 | 文案变长时仍能换行和显示 |
| 方向适应 | 使用 inline-start 等逻辑属性，检查 RTL 镜像 | 减少从左到右布局在其他语言下失效 |
| 关键操作可达 | 避免把主要动作放在容易被裁切的位置 | 调整窗口或滚动后仍能完成任务 |

**交付物：** 结构和适应性问题表；要求实现时交付布局规则、断点、间距或容器行为的调整。

**前后示例：** 设置表单使用固定两列，小屏按钮被挤出，翻译后标签溢出。修复后根据内容转为单列，标签换行，主要操作始终可达。

**验收重点：** 支持范围的最小和最大宽度、200% 缩放、长翻译和 RTL；确认关键内容与按钮没有被遮挡。

**边界：** 上游间距数值在没有现有体系时作为起点；专业工具可以保持合理的高密度。视觉层级调整不等于已验证业务流程或转化效果。

**示例请求：** “使用 better-layout 修复筛选栏在侧栏和手机宽度下的拥挤，支持更长的中文和英文标签。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-layout/SKILL.md) · [分组与对齐](sources/skills/better-layout/grouping-and-alignment.md) · [适应性](sources/skills/better-layout/spacing-and-adaptivity.md)

<a id="better-writing"></a>
## 7. better-writing · 产品界面文案

**职责：** 让操作、反馈、错误和空状态表达明确，维持产品术语、语气和语言规则的一致性。

**需要提供：** 现有文案、按钮实际行为、错误发生条件、术语表与本地化约定。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 继承产品口吻 | 先读周边文案和规范，按场景风险调整语气 | 不同页面像同一个产品写出来的 |
| 统一术语 | 相同概念采用稳定名称，避免菜单和提示使用不同叫法 | 用户无需猜测两个词是否是同一操作 |
| 动词化操作标签 | 用“保存草稿”“删除项目”等明确行动 | 仅看按钮就能预期点击结果 |
| 说明危险后果 | 确认按钮重复具体后果，取消选项明确 | 降低模糊“是/否”造成的误解 |
| 链接目的明确 | 用目的地或具体主题替代泛化“点击这里” | 单独阅读链接也知道会去哪里 |
| 开关描述开启状态 | 说明开启后会发生什么，避免双重否定 | 用户更容易理解开关状态 |
| 错误提供恢复动作 | 在出错字段旁说明原因或下一步，避免只说“失败” | 用户知道该修改输入、重试还是检查连接 |
| 空状态引导 | 说明区域用途、为何为空和一个明确下一步 | 新用户有路径继续操作 |
| 搜索无结果退出 | 说明当前条件，并提供清除过滤等出口 | 用户不被困在空结果页 |
| 本地化友好表达 | 避免拼接句子、难翻译习语，完整处理变量与复数 | 翻译时更容易保持语序和含义 |
| 提示与标签分工 | placeholder 展示格式，持久标签表达字段名称 | 开始输入后仍然知道字段用途 |

**交付物：** 按位置组织的原文、建议文案、原因和优先级；要求实施时更新源文案及项目已有翻译结构。

**前后示例：** “Oops！失败了。”改为“保存失败。检查网络连接后重试。”；空列表从“暂无数据”改为区域用途说明加“创建项目”。这些示例只有在确实支持重试或创建时才成立。

**验收重点：** 文案与真实行为一致，错误建议可执行，关键术语统一，标签不随输入消失。许多文字判断可由源码完成，最终空间表现由排版和布局检查。

**边界：** 它不负责品牌战略、营销转化验证或全量翻译服务。不能通过改文案虚构一个产品实际没有的恢复能力。

**示例请求：** “使用 better-writing 梳理项目创建流程的按钮、错误和空状态，让每处提示说明真实可执行的下一步。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-writing/SKILL.md)

## 8. interface-review · 代码变更的界面影响审查

**职责：** 先确定此次修改，再判断它新增或破坏了哪些界面行为。由用户主动调用。

**需要提供：** 可读取的 Git 仓库，以及未提交修改、暂存区、分支、PR 或明确版本范围。应能解析基线与被审查版本。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 精确范围解析 | 支持 working、staged、branch、PR 和版本范围；区分端点比较与共同祖先比较 | 报告对应用户实际请求的改动 |
| 无目标时选择范围 | 优先检查分支相对基线新增提交，并计入未提交修改；其次只查未提交修改 | 不被一处未提交格式调整遮住整个分支 |
| 覆盖新增文件 | 对包含未提交工作的范围额外检查未跟踪文件 | 新建组件不会从审查清单中消失 |
| 避免假范围 | 无改动、基线不明或处于合并中时说明情况 | 不擅自拿上一个提交冒充本次修改 |
| 排除生成内容 | 过滤锁文件、产物、第三方和二进制等，列明排除范围 | 注意力集中在有意义的界面实现 |
| 追踪受影响页面 | 默认向直接使用方扩展一层；变量与基础组件可扩展两层，最多审查五个使用方 | 发现小改动对多个页面的影响，并明确覆盖边界 |
| 读取删除部分 | 查找移除的标签、焦点、方向、换行和状态提示等，并检查是否有等效替代 | 发现“以前可用、这次丢了”的退化，减少重构误报 |
| 分类问题 | 区分 Introduced、Regression、Pre-existing | 让此次作者聚焦其实际引入的问题 |
| 对照修改意图 | 阅读 PR、提交描述等，检查主题、状态或翻译是否漏改 | 找到代码存在但需求没有完成的部分 |
| 交给领域规则 | 由 better-interface 组织诊断、排序和汇总 | 变更范围与专业判断保持分工 |

**交付物：** 基线与目标版本、文件范围、受影响页面、分类发现、独立的少量历史问题、验证与结论。

**前后示例：** 某次重构把按钮改成可点击的 div，并删除焦点样式。它需要对比旧实现、确认没有等效键盘方案，再报告退化；若只是把 aria-label 换成正确的 aria-labelledby，则不应仅因删除属性而报错。

**验收重点：** 行号对应被审查版本，删除和增加两侧都读过；每条“退化”有基线依据；历史问题不混入本次变更结论。

**边界：** 工作树默认只读，不能为了审查擅自切换用户当前分支。真实渲染按上游流程是选择性步骤，未运行需写明。通用安全、性能和业务正确性仍需其他代码审查。

**示例请求：** “使用 interface-review 检查当前分支的界面变更，区分新增、退化与历史问题，重点关注共享按钮对页面的影响。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/interface-review/SKILL.md) · [范围解析](sources/skills/interface-review/scope-resolution.md) · [删除信号](sources/skills/interface-review/removed-signals.md)

## 9. explain-interface · 网页实现机制解析

**职责：** 解释整个站点的前端实现，或某一个视觉与动画效果的形成机制。由用户主动调用。

**需要提供：** 网页 URL 或截图，以及要解释的具体对象。URL 可结合浏览器和 HTML/CSS；截图只能支持有限重建推断。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 区分全站与局部问题 | 全站检查框架线索、样式、变量和资源；局部只围绕指定效果 | 回答范围和用户问题一致 |
| 组合静态与运行证据 | HTML/CSS 提供声明与响应式规则；浏览器提供实际计算值和动画 | 更好地区分“写了什么”和“当前生效了什么” |
| 查找图层 | 检查元素、伪元素、背景、模糊和遮罩，并按绘制顺序解释 | 理解复杂效果由哪些层叠加而成 |
| 分析动画阶段 | 查看关键帧、时长、延迟和节奏，解释它们的视觉作用 | 能把分散参数转成可复用的动态设计方法 |
| 区分证据等级 | 分别标记实测、计算推导和意图推断 | 读者知道哪些结论可复现、哪些只是解释假设 |
| 识别截图限制 | 只从像素和比例讨论可观察信息，不宣称获得原源码 | 减少根据外观臆测框架、断点或精确尺寸 |
| 解释机制而非堆数值 | 说明每层作用、关键参数及其关系 | 学到能迁移到自己项目的方法 |
| 标明不可迁移项 | 说明字体许可、图片资产、品牌色和视口依赖 | 避免把参考页面的全部条件当成通用方案 |

**交付物：** 观察路径、实现机制、关键证据、证据等级、可迁移配方和不可确认项。

**前后示例：** 从“这是一个模糊渐变”推进到“底层超出容器的渐变提供色带，模糊抹平边界，上方半透明层形成朦胧感”，同时区分哪些来自真实 CSS，哪些是视觉推断。

**验收重点：** 数值有出处；区分编译后运行结果与作者源代码；检查伪元素；不要仅罗列样式读数。

**边界：** 当前正文要求以可迁移的文字配方收尾，不把复刻代码当作主要交付物。网页样式不可读取、Canvas 或 WebGL 内部实现不可见时，应说明观察边界。截图不能证明原作者用了哪种技术。

**示例请求：** “使用 explain-interface 解释这个网页标题背景的渐变和模糊如何叠加，标明测量与推断，不需要整站分析。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/explain-interface/SKILL.md) · [效果查找](sources/skills/explain-interface/find-the-effect.md) · [截图分支](sources/skills/explain-interface/from-an-image.md)

## 10. break · 组件极端场景展示与观察

**职责：** 将一个真实组件放到独立临时页面，在适用的输入和空间条件下展示，标记实际看到的破损。由用户主动调用。

**需要提供：** 一个现有组件、它的属性和数据来源、支持的状态及可运行项目。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 按组件挑选场景 | 先读属性、插槽和状态，仅保留生产中可能到达的场景 | 不对固定图标按钮硬套长文本列表测试 |
| 内容长度测试 | 空字符串、短词、正常长度、多句内容、不可断开的长串 | 观察容器塌陷、文字溢出和换行问题 |
| 内容形状测试 | Emoji、变音符、RTL、混合方向、数字等适用数据 | 发现字符裁切、垂直偏移或方向问题 |
| 数量测试 | 对列表类组件提供零、一、正常及更大量数据 | 发现空状态缺失、堆叠和滚动问题 |
| 容器压力测试 | 同页放置 320px、受相邻元素挤压和宽容器场景 | 一次加载比较不同可用空间下的表现 |
| 状态展示 | 根据组件实际支持的属性展示 loading、error、disabled | 确认异常状态是否仍可读、结构是否稳定 |
| 使用真实组件 | 导入项目组件，保留项目字体与全局样式，使用测试数据 | 减少测试页面与真实组件实现不一致 |
| 页面即报告 | 每场景有标签；已观察的失败直接写到页面上 | 用户可逐项查看并复核问题 |
| 分配修复领域 | 将破损交给布局、排版、文案等对应技能解释 | 知道后续应该在哪里修复 |

**交付物：** 临时页面及访问位置、场景清单、已观察现象与责任领域表。页面保留供用户查看，按用户要求清理。

**前后示例：** 标签列表在三个短标签时正常，但在十倍数量、一个很长标签和窄容器下发生溢出。测试页把各场景放在一起，并在实际观察到的失败场景下标注；用户要求修复后再重验对应场景。

**验收重点：** 页面使用真实组件与正确测试属性；“看见了破损”和“推测会破损”分开；没有浏览器观察时只交页面与待观察场景。

**边界：** 这是轻量的一次构建与观察流程，不自带持续回归套件、全面浏览器矩阵或性能基准。固定容器宽度检查不等同于完整视口媒体查询测试；主题、缩放与减少动态效果由真实环境切换。缺少现成浏览器时，当前正文允许交给用户查看，不能宣称已看过。

**示例请求：** “使用 break 测试标签列表组件，覆盖空数据、长标签、十倍数量和窄容器，保留可供检查的场景页。”

**来源：** [固定版本正文](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/break/SKILL.md) · [场景定义](sources/skills/break/scenarios.md)

## 11. variant · 可运行的组件设计候选

**职责：** 针对一个组件提出有意义的设计差异，默认生成三个版本，放入真实页面比较，由用户选择。由用户主动调用。

**需要提供：** 一个具体 UI 部件、所在页面、要完成的任务、已有设计变量和真实内容。

| 具体能力 | 具体做法 | 可实现效果 |
| --- | --- | --- |
| 收敛设计对象 | 每轮围绕一个部件，如指标卡或筛选栏 | 保持方案可理解、可比较 |
| 选择主要变化维度 | 在结构、密度、强调、排版、文案语气中选择一个主要维度 | 能判断差异为什么有效，而不只是“哪个更好看” |
| 形成明确方向 | 默认三个版本，给出表达方向的名称 | 候选之间有实质差别，避免只换颜色 |
| 保持共同质量底线 | 每个版本检查可访问名称、键盘、焦点、窄屏和状态表达等 | 不把明显不可用的方案当作正常候选 |
| 放进真实页面 | 保留周围导航、邻近内容和真实数据；无可承载页面时可用独立 HTML | 能判断方案与产品上下文是否匹配 |
| 全尺寸切换 | 一次显示一个方案，避免缩略图影响尺寸判断 | 真实比较间距、密度与页面高度 |
| 地址记录选择 | URL 的 variant 参数保存当前方案，浮动选择器切换 | 可以把具体候选链接发给协作者 |
| 键盘切换 | 左右键逐项切换、数字键直接选择，当前项有状态标识 | 比较操作更快速可达 |
| 解释取舍 | 说明每个方向适合什么场景、牺牲什么 | 用户基于产品需求做决策 |
| 选定后收敛 | 按项目约定落地选中方案，清理其他候选和临时比较结构 | 探索结果转为可维护的正式实现 |

**交付物：** 默认三个可运行方案、选择器、访问方式、适用条件与代价表；用户选择之后才进入最终方案落地。

**前后示例：** 同一指标卡围绕信息密度提供“宽松”“均衡”“紧凑”三种布局，使用相同指标和数据。比较时能看到一屏展示数量、描述完整度和视觉重点的差别。

**验收重点：** 主要维度明确，每个方案可运行、交互响应、基本检查通过，使用真实内容；表格说明取舍，不能把作者偏好冒充用户选择。

**边界：** 它不自动替用户选优，不验证真实用户偏好或转化率。方案选择器和临时结构是比较工具，通常在选定后清理；不是生产功能的一部分。

**示例请求：** “使用 variant 为指标卡做三个信息密度方案，保持相同数据和颜色，在实际仪表盘中切换比较并解释取舍。”

## 相近技能如何分工

| 容易混淆的情况 | 如何选择 |
| --- | --- |
| 整体页面问题 vs 本次修改问题 | 页面现状用 better-interface；分支或 PR 用 interface-review |
| 文字说什么 vs 文字如何显示 | 语义、措辞与术语用 better-writing；字体、换行、截断用 better-typography |
| 对比度是否适用 vs 如何测量修改 | 要求分类由 better-accessibility 负责；计算和配色修复由 better-colors 负责 |
| 组件好不好看 vs 内容是否撑坏 | 视觉润色用 better-ui；边界场景展示用 break |
| 空间不够 vs 字符断行 | 外层结构和空间由 better-layout 负责；文字自身换行由 better-typography 负责 |
| 想知道参考怎么做 vs 想选自己怎么做 | 参考机制用 explain-interface；自己的多个候选用 variant |
| 观察问题 vs 自动修复 | break 默认保留观察结果；需要修复时明确提出并按责任领域重新验证 |
| 有方案可比较 vs 已经确定正式版本 | variant 的候选页只是决策材料；选中、落地和清理后才形成最终实现 |

## 效果表述的三个层次

1. **本次已核实：** 固定版本存在相应规则、步骤、参考和输出约定。
2. **执行后可验收：** 生成指定报告、测试页或候选方案；代码修复后的行为需实际检查。
3. **本次没有证据：** 更高转化率、更快开发速度、所有用户体验改善或完整标准合规，均未进行测量。
