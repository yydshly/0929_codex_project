# 使用场景、交付物与验收

以下六个案例为研究构造，用于说明技能如何落到实际任务。没有实际运行这些技能，也没有展示真实修复成绩。

## 1. 一个“能用但粗糙”的账户设置页

**输入：** 账户设置页的代码与预览，包含表单、头像、通知开关、保存反馈与弹窗。

| 步骤 | 使用技能 | 具体工作 | 形成的成果 |
| --- | --- | --- | --- |
| 定位问题 | better-interface | 检查完整流程与六领域，先看阻断操作的问题 | 带位置、严重程度和覆盖说明的清单 |
| 修复操作 | better-accessibility | 补充输入标签、键盘路径、弹窗焦点行为 | 键盘可完成的设置流程 |
| 修复表达 | better-writing | 按真实失败原因提供恢复建议 | 用户知道如何继续的错误与状态文案 |
| 修复显示 | better-layout、better-typography | 处理窄屏、长标签、多行说明与截断 | 内容不遮挡主要操作 |
| 打磨细节 | better-ui | 优化图标、按压和主题切换 | 更连贯的状态反馈 |

**验收：** 纯键盘能打开、提交、关闭并继续原流程；窄屏不丢主要按钮；失败提示建议真实可用；修复清单逐条核对。

**不能宣称：** 仅完成视觉整理就提高了留存率。需要产品数据或用户研究才能支持这种结论。

## 2. 共享按钮重构即将合入

**输入：** 明确分支或 PR、基线、修改意图和按钮使用页面。

**流程：** 用户调用 `interface-review` → 解析改动和使用方 → 对照删除和新增内容 → 交给 `better-interface` 与领域规则判断 → 分类报告。

**具体检查：** button 是否被改为缺少键盘处理的 div；focus 样式是否丢失；原来的标签是否有等效替代；loading 状态是否仍明确；危险按钮是否保持区分。

**交付物：** 对应固定版本的文件位置、Introduced / Regression / Pre-existing 分类、受影响页面与未展开范围。

**验收：** 每个退化有旧版对照，等效重构不误报；历史问题与此次问题分开；没有切换或覆盖作者当前工作树。

**不能宣称：** 该审查覆盖了全部业务正确性、安全性或所有页面。当前流程的使用方扩展存在明确上限。

## 3. 标签列表准备接入真实数据

**输入：** 真实 TagList 组件，标签可由用户输入，支持 loading 和 error。

| 测试条件 | break 可以帮助发现什么 | 后续修复归属 |
| --- | --- | --- |
| 零个标签 | 是否只留下不明原因的空白 | better-writing、better-layout |
| 一个很长且不可断开的标签 | 是否撑破卡片或遮挡删除按钮 | better-typography、better-layout |
| Emoji 与混合方向名称 | 字符裁切、方向和对齐问题 | better-typography |
| 正常数量的十倍 | 包裹、滚动或结构是否失效 | better-layout |
| 窄容器与相邻元素挤压 | flex 或 grid 项是否拒绝收缩 | better-layout |
| 加载与失败状态 | 状态是否可感知、说明是否溢出 | better-accessibility、better-writing |

**交付物：** 所有适用场景组成的临时页，失败直接标在对应实例旁，另有观察表。

**验收：** 使用实际项目组件和字体，没有重写一个替代品；测试属性真正到达组件；失败必须有观察依据。后续明确要求修复时，复测同一失败场景。

**不能宣称：** 临时场景页等于自动化测试套件。持续回归需要另外接入测试和结果保存机制。

## 4. 仪表盘指标卡的信息密度拿不准

**输入：** 同一组指标数据、页面位置、用户高频查看需求与设计变量。

**流程：** 用户调用 `variant`，选择“密度”为主要变化维度，生成宽松、均衡、紧凑三个方向。颜色与数据尽量一致，辅助变化服务于密度，而不同时改变所有设计因素。

**交付物：** 实际仪表盘内可切换的全尺寸卡片、候选链接、适用场景和成本表。

| 候选方向 | 可能收益 | 需要检查的代价 |
| --- | --- | --- |
| 宽松 | 说明更完整，单个指标更突出 | 一屏展示较少，滚动增加 |
| 均衡 | 保留趋势和必要解释 | 对极长说明仍需设计处理 |
| 紧凑 | 一屏可比较更多指标 | 字号、点击区和内容完整性不能退化 |

**验收：** 每种方案可操作，真实数据可读，指定宽度下基本检查通过；用户选择后落地选中方案并清理其余候选。

**不能宣称：** 三个方案中某个已经证明最受用户欢迎。这需要另行测试。

## 5. 学习参考网站的光晕标题

**输入：** URL 与标题区域，明确只解释背景光晕，不研究整个站点。

**流程：** `explain-interface` 读取可用 HTML/CSS 和运行表现，检查伪元素、超出容器的图层、渐变、模糊与遮罩，说明每层的作用。

**交付物：** 按绘制顺序组织的机制说明、关键数值的证据等级，以及迁移到自己项目时应重新调整的参数。

**验收：** 实测值可追溯；没有把运行结果宣称为原作者源码；如果只有截图，清楚说明是在提出可能方案。

**不能宣称：** 看到了类似视觉效果就能确定框架、动画库或原始组件结构。

## 6. 深色主题上线后文字难读

**输入：** 明暗主题变量、问题组件、实际背景与透明表面。

**流程：** `better-colors` 追踪变量用途并测量实际颜色组合；`better-accessibility` 判断适用要求；用户要求修复后修改对应变量并复测；`better-ui` 检查主题切换期间是否出现大范围过渡。

**交付物：** 原始变量到语义变量的关系、失败组合、修复前后测量记录和主题检查结果。

**验收：** 两种主题分别检查；组件背景不能被页面背景代替；一个共享变量修复后，需要查看其他使用方。

**不能宣称：** 只检查几组颜色就证明整站无障碍通过。

## 通用验收卡

| 项目 | 应记录的内容 |
| --- | --- |
| 任务范围 | 页面、组件、状态、版本和支持环境 |
| 初始问题 | 实际行为或源码证据，不只写“体验不好” |
| 交付物 | 报告、代码改动、场景页或候选方案的位置 |
| 前后比较 | 使用同一内容和条件，比较指定行为 |
| 已验证内容 | 具体操作、工具与结果 |
| 未验证内容 | 原因及仍需用户或环境补充的步骤 |
| 最终判断 | 仅对已检查范围给出结论 |
