# 使用场景、组合流程与验收方式

[返回子项目](README.md) · [完整技能](SKILLS.md) · [个人采用建议](USER_VALUE.md)

以下为结合源码设计的示例方案，未实际运行。箭头表示可以由人选择推进的顺序，不表示技能会自动跨越所有阶段。示例中的任务均需放到相应授权、工具和环境中执行。

## 场景一：研究一个新的 GitHub 项目

**问题：** 看完首页只知道宣传点，不知道能力范围、是否适合自己，后续也难以找回判断依据。

| 步骤 | 可用技能或方法 | 产出 |
| --- | --- | --- |
| 明确研究目标 | grill-with-docs；目标已清楚时可直接开始 | 需要回答的问题和术语 |
| 核实事实 | research | 固定版本、第一手来源、能力与限制 |
| 保存结论 | writing-for-agents 的完成标准与信息组织原则 | 面向后续查阅的研究文档 |
| 需要换会话或工具时交接 | handoff | 待核实问题和已有成果指针 |

**输入：** 仓库地址、研究目标、当前工作目录和已有收录规范。

**示例请求：** “研究这个库的能力、技术原理、技能清单、适用场景与采用价值；覆盖非首页目录，区分源码事实与实测结果。”

**验收：** 能准确回答每个研究问题；清单与目录一致；重要主张可追溯到版本；写明未验证范围；下一位读者能找到下一步。

**边界：** research 原流程要求后台代理；单代理完成同样的资料核对属于方法借鉴，不应声称获得并行加速。本次研究即以固定版本源码核对为主，没有启用上游技能。

## 场景二：把研究集做成可搜索的本地演示

**问题：** 已有很多研究文档，想按主题、用途或验证状态找到项目。

建议路线：`grill-with-docs → prototype → to-spec → to-tickets → implement`，其中实现过程使用测试与审查。

先定义“项目”“标签”“已验证”等含义，再用原型确定卡片或表格展示方式。规格确认后，可拆为：

| 任务 | 可展示的结果 | 依赖 |
| --- | --- | --- |
| 读取并展示一个真实项目 | 用户能看到真实标题和研究链接 | 无 |
| 按名称搜索 | 输入关键字得到正确结果 | 展示数据 |
| 按标签和验证状态筛选 | 多条件组合行为符合约定 | 展示数据 |
| 展示空结果和来源信息 | 没有匹配时能理解原因，并能访问来源 | 搜索、筛选 |

**验收：** 使用真实元数据演示；搜索预期可复现；文档链接可用；明确演示是否联网、是否持久化。

**边界：** prototype 是验证设计的临时产物，不代表完整产品。网站部署、域名和托管仍是额外工作。

## 场景三：一个功能反复修不好

**问题：** 刷新后筛选条件丢失，AI 多次改动仍无法稳定解决。

建议用 `diagnosing-bugs`，而非先把可能相关的文件都重写。

1. 用最短操作路径复现“选择条件 → 刷新 → 条件丢失”。
2. 建立能分辨正确和错误结果的命令或浏览器检查。
3. 缩小到真正影响结果的状态、存储和初始化步骤。
4. 提出可检验原因，一次改变一个变量。
5. 修复后重新执行原始场景，并保留合适的回归测试。

**产出：** 复现步骤、原因证据、修复和验证结果。

**验收：** 必须覆盖用户报告的症状，不能只证明“应用启动了”。

**边界：** 无法获得复现环境时，技能本身不能凭空恢复事实；应记录缺口。

## 场景四：一个大想法需要多次讨论

**问题：** 想做“个人研究与知识管理平台”，但导入、搜索、更新、引用、协作都没有想清楚。

建议先用 `wayfinder`。把不确定问题写成决策任务，例如：

| 决策问题 | 为什么要先解决 | 可能的处理方式 |
| --- | --- | --- |
| 数据是本地文件还是远程服务 | 影响同步、隐私与运行环境 | 研究和讨论 |
| 搜索是关键词还是语义检索 | 影响成本和解释性 | 原型与研究 |
| 什么算一次研究完成 | 影响界面状态与工作流程 | 需求澄清 |
| 上游版本更新怎样标记 | 影响来源追溯和维护 | 讨论与小实验 |

**产出：** 决策地图、每项结论及依据。关键未知解决后，再形成规格和实施任务。

**验收：** 地图的终点明确；已解决问题不再反复讨论；不能确定的问题没有被假装成实施任务。

**边界：** 这一步主要在规划，不能以写了很多 Issue 作为产品已经完成的证据。

## 场景五：接收外部需求与错误反馈

**问题：** 用户说“搜索不好用”“想要导出”，信息不完整，团队不知道哪些可以做。

用 `triage` 读取背景、验证声明并分类；需要别人补信息时可用 `to-questionnaire`。

**产出：** 待补信息、可交给代理的任务简报、需人工判断的事项，或有理由的拒绝记录。

**验收：** 每个条目的当前状态清楚；下一步由谁完成清楚；已问过的问题不会重复问。

**边界：** 配置之外的外部 PR 不一定纳入；更改标签、评论和关闭条目属于对外操作，需匹配实际授权。

## 场景六：检查已完成的实现

**问题：** 功能能运行，但不清楚是否漏了验收要求。

用 `code-review`，分别检查规范和规格。两个方向回答：

- 写法与结构是否符合项目约定？
- 实现是否覆盖需求，有无擅自扩展或错误解释？

**产出：** 两份可定位的问题报告。

**验收：** 审查基准明确、实际变更文件进入范围、需求问题指向具体规格。

**边界：** 未提交的工作区改动不能默认被 HEAD 差异涵盖；没有规格时必须明确需求维度缺失。

## 场景七：调整难以维护的代码

**问题：** 修改一个概念要跳转很多文件，测试大量依赖内部细节。

路线：`improve-codebase-architecture → codebase-design → 澄清选中的方案 → 规格/实施`。

**产出：** 前后结构对比、改进候选及强度、选中方案的接口设计。

**验收：** 说明真实修改困难；接口更容易使用；测试与调用者使用同一对外行为；没有仅为“看起来规范”增加抽象。

**边界：** HTML 分析报告不是重构完成证明；候选建议仍需结合团队经验判断。

## 场景八：跨工具或跨会话接着研究

**问题：** 当前会话很长，想把后续任务移到新目录或交给别人。

用 `handoff` 保存目标、当前结论、成果位置、未解决问题和建议技能。

**验收：** 接手者能通过链接获取主要资料；只需读取必要背景就能继续；正式成果不只存在于临时文件中。

**边界：** handoff 不自动创建或唤醒任务。`claude-handoff` 才尝试启动 Claude 后台进程，而且属于实验、平台专用路径。

## 场景九：把研究变成学习与写作

| 目标 | 技能 | 成果与验收 |
| --- | --- | --- |
| 系统理解一个主题 | teach | 短课、练习、参考资料；能独立完成具体练习 |
| 解释没听懂 | wait-what | 用中文补足背景；能准确复述 |
| 收集个人经验 | writing-fragments | 保留原始观点和案例 |
| 形成文章论证 | writing-shape | 段落顺序服务于同一论点 |
| 精细选择叙事路线 | writing-beats | 每一步概念铺垫充分 |

**边界：** 三个写作技能属于实验目录。它们需要较多互动，不适合期待立即得到一篇不需讨论的成稿。teach 生成的学习资料也需要核对事实与文件依赖。

## 场景十：把重复活动设计为自动化

**问题：** 每周重复整理项目笔记，想减少机械工作。

用实验技能 `loop-me` 明确触发、输入、处理过程、人工决策点和最终简报。

**产出：** 可实施的工作流规格，例如“新项目研究完成后更新索引；只在来源缺失时请求人工处理”。

**验收：** 每步输入输出明确；失败如何处理明确；需要人决定的事项明确。

**边界：** 保存规格不等于已经创建自动化。调度器、通知渠道和外部服务连接需另行实现。

## 按投入选择流程

| 任务大小 | 建议组合 |
| --- | --- |
| 一个事实问题 | 直接检索或研究方法；不建完整规格 |
| 一次小研究 | research 的来源方法 + 简洁结论 |
| 一项明确功能 | implement + 合适的测试和审查 |
| 跨会话功能 | 澄清 → 规格 → 任务 → 分项实施 |
| 不确定的大型工作 | wayfinder → 规格与任务 |
| 一段表达不清 | wait-what |
| 需要真正搬移上下文 | handoff |

本表是研究者的采用建议，重点是让流程成本与问题规模匹配。
