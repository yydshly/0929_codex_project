# 从实际场景理解技能

[打开交互演示](web/index.html) · [返回子项目](README.md)

6 个场景、18 个分步样张，涵盖 18 个技能。场景为根据固定版本源码设计的教学演示，不是上游技能执行日志。三个小组件分别提供原型筛选、故障与修复对照、概念理解练习。其他 20 项技能保留在完整能力目录中，尚未制作分步样例。

## 拿到一个仓库，判断与自己有没有关系

你拿到一个 GitHub 链接。首页介绍很丰富，但你真正关心的是：它解决我的哪类问题？需要写代码吗？哪些内容值得继续看？

**什么时候值得用：** 你准备为一个工具投入学习时间，或需要向别人解释选型理由时。

**什么时候不必用：** 只想知道一句话定义，且后续不会据此做决定时，普通问答通常就够了。

**原始材料**

```text
已知材料：仓库链接、首页介绍。
你的目标：判断是否值得深入，不想先学安装和调用。
缺少的信息：完整能力范围、实际成果、与你的任务的对应关系。
```

**示例依据：** 事实基于本项目已核对的固定版本；下面的推进过程与文档样张为教学重组，不是上游技能执行日志。

### 先把“值得研究”说清楚

对应技能：[grill-me](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/grill-me/SKILL.md)

否则回答容易变成把所有功能都介绍一遍，却没有回答你是否需要。

- 把笼统的“这个库好不好”收敛到一个决定。
- 区分你的真实任务与仓库擅长的任务。

**示例：研究问题与取舍**

```text
本次要决定：哪些能力值得用在我的开源项目研究里？

优先看：来源核实、成果展示、知识解释、跨会话交接。
暂时跳过：Git 冲突、TypeScript 测试迁移、课程目录搭建。
完成标准：每个优先能力都能说明一个输入、一个成果和一个限制。

这里的优先级是针对当前任务的判断，不是上游的技能排名。
```

**检查成果：** 能说出研究结束后要作出的决定，而不是只说“全面了解”。

### 核对能力范围与证据

对应技能：[research](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/research/SKILL.md)

首页概述与完整目录可能不一致，结论需要对应到具体版本和文件。

- 枚举技能入口，对照正式插件清单。
- 将事实、解释和未验证的部分分开保存。

**示例：带依据的结论摘录**

```text
研究版本：c55ee460

事实 A：全仓库有 38 个 SKILL.md。
事实 B：正式插件收录 25 个；另外 9 个实验、4 个专项。
事实 C：research 强调第一手来源；handoff 交付接手所需的上下文。

对我的判断：先看 research、handoff、teach；需要做页面时再看 prototype。
未验证：没有安装上游技能，没有测量节省多少时间。
证据入口：技能正文、插件清单和本项目来源清单。
```

**检查成果：** 事实能追溯来源；“适合我”作为判断单独呈现。

### 避免把“研究完”写成“验证过”

对应技能：[domain-modeling](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/domain-modeling/SKILL.md)

同一个“完成”如果有不同含义，后续很容易误判资料的可信范围。

- 为相似状态给出清楚定义。
- 用一个反例检验定义是否真的能区分。

**示例：项目状态词汇表**

```text
研究完成：已阅读、汇总并核对能力与来源。
运行已验证：已在具体环境中执行并保存结果。
已发布：网页已经可从公开地址访问。

当前示例：研究完成；网页本地可浏览；上游技能未运行验证。
反例：有一张网页截图，只能证明页面渲染，不能证明 38 个技能都运行成功。
```

**检查成果：** 看到一个状态就能知道已完成什么、还不能声称什么。

**最终得到：** 一页可复查的能力判断：哪些值得看、哪些暂时跳过、依据在哪里。

## “我想要一个网页”，怎样变成可验收的成果

你有三条工具研究笔记，想做一个方便查看的网页。你不想参与实现细节，但需要确认做出来能解决问题。

**什么时候值得用：** 同一个想法需要经历讨论、实现、验收，或者你已经遇到过“做出来不是我想要的”。

**什么时候不必用：** 只改一个标题或颜色，没有范围与验收分歧时，不必走完整流程。

**原始材料**

```text
原始想法：把这些工具做成一个好看、好用的网页。
样例资料：线索台（研究）/ 灵感簿（写作）/ 练习卡（学习）。
尚未确定：谁来用、怎样查找、什么算做好。
```

**示例依据：** 这是缩小后的虚构项目；下面可操作的三条数据用于展示原型与验收的关系。

### 把模糊要求变成共同理解

对应技能：[grill-with-docs](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/grill-with-docs/SKILL.md)

“好用”不能直接验收；要先知道你实际会怎样找资料。

- 围绕查找资料的任务澄清目标。
- 把已经确定的取舍保存下来，避免下次重新解释。

**示例：已确认的需求**

```text
使用者：我自己，偶尔给同事查看。
常见动作：按名称或简介找工具；区分研究、写作、学习。
重要取舍：先把能力与成果讲清楚，再追求视觉丰富。
本次范围：浏览、搜索、分类、无结果提示。
暂不做：账号登录、自动抓取、多人编辑。
```

**检查成果：** 另一位接手者能解释目标和范围，不需要猜“好用”是什么意思。

### 把讨论写成可以判断对错的规格

对应技能：[to-spec](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/to-spec/SKILL.md)

讨论结论需要变成明确行为，否则“已实现”可能只代表页面上有一个搜索框。

- 综合已有共识，不重新发起整轮需求采访。
- 写出用户故事、实现决策、测试边界和范围外事项。

**示例：功能规格摘录**

```text
用户故事：我想用“写作”找到名称中没有这个词、但简介包含它的工具。

约定行为：
1. 搜索范围包括名称与简介。
2. 分类和关键词同时生效。
3. 清空条件后恢复全部 3 项。
4. 无匹配时显示说明和重置入口。

验证位置：通过页面操作检查显示结果。
范围外：联网推荐、个性化排序、账户同步。
```

**检查成果：** 用“写作”搜索时，能确定应该出现哪条，而不是只看搜索框能否输入。

### 先亲手试一下再决定

对应技能：[prototype](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/prototype/SKILL.md)

操作样本能暴露口头讨论中看不出的查找体验。

- 用少量固定数据演示关键交互。
- 把试用后确认的行为反馈到规格中。

**示例：原型确认记录**

```text
请在下方样本中搜索“写作”，再切换到“研究”分类。

应观察到：
• 全部分类下找到“灵感簿”，因为简介包含“写作”。
• 研究分类下没有匹配项，说明两个条件同时生效。
• 重置后恢复 3 项。

本阶段只确认操作与规则，不证明正式数据、权限或异常处理已经完备。
```

**检查成果：** 能根据亲手操作决定保留什么行为，以及是否需要修改规格。

### 把约定拆成可以交付的任务

对应技能：[to-tickets](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/to-tickets/SKILL.md)、[implement](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/implement/SKILL.md)

规格回答“需要什么”，任务拆分与实施才落实到可检查的变更。

- 按可验收的成果拆分任务并说明依赖。
- 实施后运行适用检查、审查变更并汇总结果。

**示例：任务与验收记录格式**

```text
任务 A：展示三个条目的名称、简介与类别。
验收：三个条目完整显示。

任务 B（依赖 A）：支持名称、简介搜索及类别组合筛选。
验收：搜索“写作”得到“灵感簿”；加“研究”条件后无匹配。

任务 C（依赖 B）：补齐空结果与重置交互。
验收：重置恢复 3 项，手机上仍可操作。

正式交付应补充：实际修改位置、检查结果、未完成事项。
本样张未声称执行了上游实施技能。
```

**检查成果：** 每个任务都交出一个能看见的结果，而非只有“完成前端”这样的模糊描述。

**最终得到：** 你能看到并判断页面行为，再把共识交给实现者。

## 零散观察，整理成别人读得懂的分享

你研究了这个技能库，记下了几条感受。现在希望向朋友解释：为什么有很多技能，自己却只需要少数几个。

**什么时候值得用：** 手里有真实观察或材料，但不清楚怎样组织，或者需要反复积累素材时。

**什么时候不必用：** 只改一句话或调整语气时，直接编辑即可；没有经历和证据时，不应让它补造。

**原始材料**

```text
零散材料：
• 仓库共有 38 个技能。
• 很多是工程协作相关，我平常不常用。
• 看了名字仍不知道能得到什么。
• 具体例子比分类表更容易理解。
• 这次只做了源码研究，不能声称节省了时间。
```

**示例依据：** 文章样张仅使用上方材料。写作技能在实验目录；这里展示的是成果形态，不是作者原文或真实发布记录。

### 先把观察保存成有用的素材

对应技能：[writing-fragments](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/in-progress/writing-fragments/SKILL.md)

过早写成完整文章，容易把具体观察抹平成泛泛的观点。

- 保留实际遇到的困惑和判断。
- 标出证据与暂时缺少的材料，不急于排序。

**示例：素材卡片**

```text
观察：技能名称不能让我直接想到使用场景。
具体困难：知道 handoff 是“交接”，仍不清楚换会话时要留下什么。
转折：看到目标、已完成、证据和下一步的交接样张，就能判断是否有用。

事实：固定版本含 38 个技能。
观点：选技能可以先从自己的问题出发。
缺少的证据：实际节省的时间。文章不要写量化收益。
```

**检查成果：** 素材中保留了具体困惑与事实，没有先编一个漂亮结论。

### 选择文章想让读者明白的事

对应技能：[writing-shape](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/in-progress/writing-shape/SKILL.md)

把素材逐条罗列还不是文章，需要一个读者能够跟随的观点。

- 确定读者已有知识与候选开头。
- 按每段对读者的作用，逐段组织已有素材。

**示例：两个开头与选定结构**

```text
角度 A：一个技能库有 38 项能力，为什么我只想先看三四项？
角度 B：我看得懂每个技能的名字，却不知道什么时候会用到。

示例选择 B：从“看懂名称但不会对应任务”的困惑进入。
第一段：描述困惑。
第二段：用交接样张说明什么叫具体成果。
第三段：提出按自己的任务筛选，而非按数量收集。
收尾：说明尚未实测，保留判断边界。
```

**检查成果：** 开头提出的问题，能被后续段落真正回答。

### 让读者一步步得到结论

对应技能：[writing-beats](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/in-progress/writing-beats/SKILL.md)

它是另一种重视逐步叙事的写作方式，可替代或补充文章组织，不是每次必经的第三阶段。

- 先落地一个具体困惑，再引入“按成果选择”的概念。
- 只用已有材料推进，不把示例写成真实验证。

**示例：可独立阅读的短文**

```text
看懂技能名，不等于知道它能帮我做什么

我读这个库时，能理解“研究”“交接”等名称，却仍想不到它们与我的工作有什么关系。38 个技能听起来很多，但其中不少面向我不常做的工程任务。

交接文档的例子让我容易理解了一些：如果换一个会话，只留下“继续研究”，接手者需要重新找背景；如果留下目标、已完成的判断、证据位置和下一步，就有了继续工作的起点。

所以我更愿意先问：现在最容易反复解释、丢失或做错的事情是什么？再看哪个技能能留下对应成果。这样选择，不必把整个库都用起来。

这些判断来自源码研究和说明性例子。我还没有运行上游技能，因此暂不评价它们到底能节省多少时间。
```

**检查成果：** 文章能独立读懂，每项事实有材料来源，没有添加不存在的经历或收益。

**最终得到：** 保留真实材料，形成观点明确、可独立阅读的短文。

## 明天换个会话，接着今天的研究

这次研究已经有文档和网页。你准备结束会话，之后还希望继续补充实际场景，不想再解释前因后果。

**什么时候值得用：** 工作跨天、跨会话或需要别人接手时。

**什么时候不必用：** 任务已经彻底结束、没有后续动作时，不一定需要单独交接文档。

**原始材料**

```text
模糊交接：这个库研究好了，网页也做了，后面继续优化。
问题：研究好了指什么？网页在哪？下一步应该先改什么？
```

**示例依据：** 路径和研究版本来自当前子项目；交接内容是示例摘录，不会自动创建新会话或发送消息。

### 把聊天浓缩成接手需要的信息

对应技能：[handoff](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/handoff/SKILL.md)

完整聊天太长，一句话又丢失信息；交接应保存继续工作所必需的上下文。

- 提炼目标、状态、重要决策与未解决问题。
- 给出资料位置和接手后的第一步。

**示例：当前研究的交接摘录**

```text
目标：让使用者看懂 mattpocock/skills 的具体能力，重点是场景和成果。
用户偏好：已经知道技能用法，不需要安装教程。

已完成：核对固定版本 38 项技能；制作中文能力目录和静态网页。
版本：c55ee460；上游技能没有运行验证。
资料目录：projects/003-mattpocock-skills/
关键文件：CAPABILITIES.md、SOURCES.md、web/index.html。

下一步：先阅读 scenario-demos.json，核对各场景是否准确对应技能正文。
验收：用户能从场景看到输入、处理重点、成果和局限。
不要误写：网页演示可操作，不等于上游技能已执行。
```

**检查成果：** 接手者知道先打开什么、继续做什么，以及哪些事情不能当作已验证。

### 把反复提醒变成可复用的项目要求

对应技能：[writing-for-agents](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/writing-for-agents/SKILL.md)

handoff 保存这次进展；指令文档保存每次任务都适用的规则，两者不能互相替代。

- 把笼统偏好转成可检查的要求。
- 限定规则范围，避免把一次任务的临时决定永久化。

**示例：研究项目的完成要求**

```text
适用范围：本研究集新增的技能库分析。

每项能力至少写明：
• 解决的具体问题；
• 可以留下的成果；
• 适用条件与限制；
• 固定版本来源。

示例必须区分：源码事实、说明性演示、真实执行结果。
有网页时：检查筛选、详情、手机布局，并更新项目入口。
完成时：列出未验证事项。

这些是本项目示例规则，不是自动向其他项目生效的全局要求。
```

**检查成果：** 规则能够检查，且不会与本次交接中的进度信息混为一谈。

**最终得到：** 接手者能找到文件，并从明确的一步继续。

## 术语看不懂，用一个小练习理解

你总看到“原型”“实现”“验证”，但不容易判断页面能点了，究竟代表项目完成了多少。

**什么时候值得用：** 你希望多次学习并积累理解，而不是只查一次术语时。

**什么时候不必用：** 只需要一个定义时直接解释即可；一次选择题也不能证明长期掌握。

**原始材料**

```text
学习目标：看到一项成果，能判断它证明了什么。
已有理解：知道网页可以交互。
当前困惑：网页能点，是否就说明系统能正式使用？
```

**示例依据：** 下面的短课与反馈为原创教学样例。答题只影响当前页面，不记录个人学习数据。

### 围绕一个真实困惑设计短课

对应技能：[teach](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/teach/SKILL.md)

把一堆术语讲完，不如先让你能做出一个具体判断。

- 围绕学习目的选择一个小目标。
- 把概念说明、练习与复习资料组织在一起。

**示例：本节短课**

```text
本节目标：区分“交互已演示”和“系统已验证”。

原型：先用小样本看看设计与操作是否合适。
实现：把约定行为接到需要的数据与功能上。
验证：通过具体检查，说明哪些行为确实符合约定。

小例子：下方三条固定数据能够搜索，只能直接证明这三条样本上的交互；不能证明十万条数据的速度，也不能证明账号权限正确。
```

**检查成果：** 能说清一项证据的证明范围，而不是只记住三个名词。

### 仍不明白时换一个解释起点

对应技能：[wait-what](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/wait-what/SKILL.md)

重述可以补上读者缺少的前提；它本身不会替你重新核实事实。

- 从已经能理解的例子开始，补足省略的背景。
- 用更少术语把区别重新讲清楚。

**示例：换一种说法**

```text
把原型想成先摆出来试走的展台：你能检查入口好不好找、卡片是否看得清。

但试走展台，并不意味着仓库里的所有货已经接好、付款系统也已经验证。

同样，眼前的搜索样本能帮你决定“这种查找方式是否顺手”。要判断正式项目完成了没有，还得对照真正的数据、功能范围和验收结果。

这里按中文语境重述；原技能偏向用更简单的英语解释。
```

**检查成果：** 能用自己的话说明“这个演示证明了什么、还没证明什么”。

### 为下次学习留下明确起点

对应技能：[teach](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/teach/SKILL.md)

下次从真实困惑继续，比每次重新上一遍入门课更有针对性。

- 保留关键收获和仍待检验的问题。
- 把简明参考资料与学习记录分开。

**示例：复习卡与学习记录模板**

```text
复习卡：
看到成果时，先问三件事：输入是什么？观察到什么？还能推断到哪里？

学习记录（待实际回答后填写）：
• 我对原型的解释：____
• 我原先误以为它能证明：____
• 我现在仍分不清：____
• 下次练习：判断一份测试截图能否证明整个系统没问题。

未作答前，不填写“已掌握”。
```

**检查成果：** 记录反映真实回答，不会因为翻过一页就宣布掌握。

**最终得到：** 一个能辨别边界的小知识点，以及下次可以复习的记录。

## 搜索明明有资料，为什么显示零条

资料“灵感簿”的简介包含“写作”，但搜“写作”找不到。你只想问题被修好，不想靠反复碰运气改代码。

**什么时候值得用：** 可以复现的问题、修完又坏的问题，或需要给修复留下证据时。

**什么时候不必用：** 如果行为本身还没约定，先确认需求；不能把所有不满意的结果都判断为程序错误。

**原始材料**

```text
预期：按名称或简介搜索。
样本：名称“灵感簿”；简介“整理写作素材”。
观察：输入“写作”返回 0 项；输入“灵感”却能找到。
```

**示例依据：** 故障被刻意放在下方独立样本中，不是当前网页目录的真实缺陷。切换按钮仅切换样本搜索规则。

### 先让问题稳定出现

对应技能：[diagnosing-bugs](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/diagnosing-bugs/SKILL.md)

只有“搜不到”这句描述，无法分清数据缺失、筛选限制还是搜索范围错误。

- 固定数据、输入和预期，建立最小复现。
- 改变一个条件观察差异，缩小原因范围。

**示例：诊断记录**

```text
复现数据：灵感簿｜整理写作素材。
复现输入：写作。
期望：1 项；故障规则下实际：0 项。
对照输入：灵感。故障规则下实际：1 项。

样本原因：搜索只看名称，没有检查简介。
最小修复：把简介纳入搜索范围。
仍需确认：正式项目是否约定了其他字段、大小写和多个关键词规则。
```

**检查成果：** 原因能够解释这两个对照结果，而不是只凭一次猜测。

### 让检查捕获这个问题

对应技能：[tdd](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/tdd/SKILL.md)

修好一次还不够，要让相同行为以后被破坏时能被检查发现。

- 先描述用户可观察的预期行为。
- 确认故障规则无法满足预期，再用最小实现通过相同检查。

**示例：行为检查，而非虚构测试日志**

```text
检查用例 A：名称不含“写作”、简介含“写作”时，应找到该条目。
检查用例 B：名称含“灵感”时，仍应找到该条目。
检查用例 C：空关键词时，应显示全部样本。

下方交互面板会实际计算当前规则对这些用例的结果。
正式项目还应在自己的检查环境中保存证据。
这里只演示行为与检查的关系，不代表已运行上游 TDD 技能。
```

**检查成果：** 同一个用例能区分故障与修复，且没有为了通过检查偷偷改变预期。

### 检查这次修改有没有偏离约定

对应技能：[code-review](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/code-review/SKILL.md)

测试覆盖的是具体例子；审查再对照需求和变更寻找遗漏。

- 确认搜索范围的改动与需求一致。
- 核对相关行为是否受影响，并说明审查范围。

**示例：审查意见摘录**

```text
已对照：规格要求同时搜索名称与简介。
本次修复方向：从仅检查名称改为检查名称与简介。
应复查：分类条件与关键词仍然同时生效；空输入和无匹配提示没有回归。

审查范围要求：包含本次全部修改。
注意：如果审查基于已提交差异，未提交的修复可能未进入审查范围。

结论形式：列出具体问题和依据；无发现也不等于证明所有情况都正确。
```

**检查成果：** 能知道审查实际覆盖了哪些修改，不把“有人看过”当作质量保证。

**最终得到：** 从“找不到”变成一条清楚的原因、一项最小修复和可以重复的验证。
